## Step 1: API, OpenAPI, generated client, dashboard data layer

**What changed**

- **`openapi/fenvix-api.yaml`.** OpenAPI 3.1 with 41 dashboard operations and 4 runner operations.
  - Every record the screens show is a schema.
  - `x-fenvix-role: admin` marks the 10 operations that need an owner or admin.
- **`src/api/schema.d.ts`.** Generated by `npm run api:generate` (openapi-typescript).
  - `src/data/types.ts` re-exports every record from it.
  - `npm run build` starts with `api:check`, which regenerates the file and fails if it differs.
  - So renaming a field in the OpenAPI file breaks the dashboard build until the screens follow.
- **The API (`github-app/src/api/`).** A Fastify plugin in the GitHub App service.
  - Routes and request validation come from the OpenAPI file: `openapi.gen.ts` is the bundled copy, and a test fails if it is stale.
  - Order of checks on every call: Supabase token verified against the JWKS (ES256/RS256/EdDSA only) → request validated → organization membership (`X-Fenvix-Workspace`) → role.
  - A missing token is 401. Another organization's ids answer 404, the same as ids that do not exist, so ids cannot be probed. A member calling an admin operation gets 403.
  - Responses are computed with the dashboard's own `src/data/ci.ts` and `ci-rows.ts`, so the mock and the API cannot disagree.
- **Database access (migration `0014_dashboard_api.sql`).**
  - The API connects as the new role `fenvix_api` (no BYPASSRLS) through the Supabase pooler in transaction mode.
  - Each request is one transaction that sets `app.user_id` and `app.workspace_id`.
  - **Row level security is the second barrier.** The policies use `api_workspace()` / `api_admin_workspace()`, which check membership and role in the database again.
  - **The browser reaches nothing.** `anon` and `authenticated` lost every right and policy on our tables, sequences and future tables.
- **Lambda.** `github-app/src/lambda/api.ts`, and an `Api` function in `infra/github-app/lib/stack.ts`.
  - It has its own role and log group, and reads only `api-database-url` and `state-signing-key` from SSM.
  - It may send to the work queue. It never holds the App's private key, the webhook secret, the OAuth secret or a runner token.
  - Routes: `ANY /v1/{proxy+}` goes to the API; `/v1/runner/{proxy+}`, `/webhooks/github`, `/github/setup` and `/healthz` stay on the App's http function.
  - CORS is allowed for the dashboard's origin only.
  - `github-app/src/api/local.ts` runs the same API as a plain Node server for development.
- **Dashboard data layer.**
  - `src/data/api.ts` + `api-browser.ts`: every call goes through `openapi-fetch` with the generated `paths`, the Supabase session's token and `X-Fenvix-Workspace`.
  - Organizations, members and invitations also go through the API (`/me`, `/organizations`, …).
  - Supabase is used for sign-in only. `src/data/supabase.ts` and the old control-plane client files are deleted.
  - Default backend is the API (`VITE_API_URL`). The mock (`VITE_DATA_BACKEND=mock`) is for local development and the Playwright checks; it produces the same shapes with the same `ci.ts` functions.
- **Live run view.**
  - `GET /v1/runs/{id}` answers with an `ETag` (from the run's `updated_at` and `progress_at`) and `304` for `If-None-Match`.
  - `src/lib/useLiveRun.ts` polls every 4 s, only while the run is running and the page is visible. It stops when the run ends or the page is hidden, and resumes when the page is visible again. No WebSocket.

## Step 2: GitHub connected end to end

**What changed**

- **Install link.** `POST /v1/github/install-link` (owner or admin) returns `https://github.com/apps/<slug>/installations/new?state=<signed: organization, person, 1 h>`.
- **Setup redirect.** The App's `/github/setup` checks three things: the state, the OAuth code, and that the installation is one the person can see on GitHub. It then links the installation and redirects to `/projects/connect?github=connected&installation=<id>&account=<login>`. It can also redirect with `?github=error&reason=…` (8 reasons) or `?github=requested`. The Connect page shows each case in words.
- **Setup pull request by GitHub repository id.**
  - `POST /v1/github/repositories/{repositoryId}/setup-pull-request` queues `{kind: "onboard", repositoryId}` and answers 202.
  - The worker opens or finds the pull request.
  - The dashboard asks for the repository list again until the state moves.
- **Onboarding states.** All 9 are mapped (`pending`, `pr_open`, `merged`, `closed`, `no_workflow`, `no_test_job`, `already_fenvix`, `unsupported`, `failed`). Each has a plain-English label, the App's detail, the workflow file and job, and the pull request link.
- **Language and test runner are detected, not hardcoded.** The App used to label every run's project `python`/`pytest`. Now it uses, in order:
  1. the workflow analysis;
  2. the summary's optional `language` / `test_runner`;
  3. the runtime (`detpy==` → Python/pytest; `detjs` → Node with vitest or jest).
  If none of these says, no project is created. A Node repository is never labelled pytest.
- **Several installations per organization.**
  - The Connect page lists every installation with its status (active / suspended / deleted), its account, repository selection and repositories.
  - "Add another GitHub account" fetches another install link.
  - Linking a second installation does not restart the trial.
  - A repository moved between installations keeps its project and its runs.

## Step 4: new features

- **(a) 30-day shadow trial, at the top of Overview.**
  - Shows: would-have-saved skip share (time-weighted over the trial's finished shadow runs), minutes, run units (not billed during the trial), days left and end date, and the 35% gate as met or not met.
  - Rules:
    - the trial starts when the organization links its first installation (`gh_link_installation`);
    - jobs then run with `FENVIX_MODE=shadow` and their runs get `mode: shadow`;
    - the run page says "nothing was skipped; N tests would have been".
  - The calculation is `trialFrom` in `src/data/ci.ts`; the gate is `TRIAL_GATE = 0.35`.
- **(b) Audit reruns in Skip with proof.**
  - Shows: tests rerun, wrong skips (expected 0), the rule-of-three bound (with 0 wrong skips in n reruns, the wrong-skip rate is below 3/n with 95% confidence; no bound once a wrong skip is found), untrusted cache keys, and the latest audited tests.
  - Data: run counters plus `ci_audit_reruns`; calculation `auditFrom`.
- **(c) GitHub installation status and per-repository onboarding.** On Connect: installation status, each repository's onboarding state and detail, and its setup pull request.
- **(d) Region per organization.**
  - `us` or `eu`, stored on `workspaces.region`. Owners and admins edit it in Settings; members read it.
  - **Used for placement:**
    - the App's launcher places each job's machine in the organization's region (`RUNNER_PLACEMENT`: AWS region and launch template per region, set by the CDK);
    - an organization whose region has no placement gets no machine; its job is never run in another region;
    - the region is recorded on the job and the run, and passed to the machine as `FENVIX_REGION`.
- **(e) Billing in run units.**
  - 1 unit = 10 baseline minutes. Baseline minutes = tests run + tests skipped with proof + other steps, the job's minutes without fenvix.
  - Counted on billable usage events only. A month's units are the exact sum rounded up.
  - Usage shows units per project. The rows add up to the total, including a row for repositories that are not projects.
  - Plans: Starter $129, Team $479, Scale $1,350, Monorepo $4,200, plus "Nightly exploration" as a paid add-on.
  - The Nightly exploration page says it is an add-on when the organization does not have it.
- **(f) API keys.** The page and its navigation entry stay, showing "Coming soon"; there is no list or form until the public API exists.

## What the runner must send

The full contract is in `docs/data-contract.md`, "What the runner sends" (request schemas: operations tagged `runner` in `openapi/fenvix-api.yaml`). The runner lives in another repository and was not edited.

Every call carries the machine's own credential (`Authorization: Bearer fxr1…`). Each record names its job by `runId`, `runAttempt`, and optionally `repositoryId` / `runnerName`, which must match the credential. Answers: `202` = accepted; `4xx` = do not retry; `5xx` = retry with backoff.

1. **Progress: `POST /v1/runner/progress`.**
   - When: at the start of each phase (`setup`, `collecting`, `testing`, `reporting`), at most every 3 s while tests run, and once when the test step ends.
   - Fields: `seq` (increasing; older ones are ignored), `phase`, `testsTotal` (null until collected), `testsDone`, `passed`, `failed`, `skippedWithProof`, `currentTest`, `elapsedMs`, `mode`.
   - It is written at once and feeds the live run view.
2. **Results: `POST /v1/runner/results`.**
   - When: in numbered chunks (≤ 5,000 tests, 2,000 receipts, 500 defects, 5,000 audit reruns, 6 MB each; chunk 0 carries `chunks`), before the summary.
   - Run fields: `engineRunId`, `seed`, `mode`, `missDetails`.
   - `tests[]`: outcome, duration, `failure` (`real` or `flaky_defect` with the bundle's `defectFingerprint`), `cacheKey` for skipped tests, `wouldSkip` in shadow mode.
   - `receipts[]`: the `receipts.jsonl` line plus the `proof-cache.json` lists (code units, modules, files read, env read, runtime, config, `changedFilesProven`).
   - `defects[]`: `bundle.json` + `order.txt` with **the engine's replay command**.
   - `audit[]`: `confirmed` or `wrong_skip`, `untrusted` for keys the engine stopped trusting.
3. **Summary: `POST /v1/runner/summaries`.**
   - `summary.json` as today.
   - Optional additions: `language`, `test_runner`, `mode`.
4. **Exploration: `POST /v1/runner/explorations`.** After a night of `detpy explore` (the add-on): the `explore.json` summary and its defect bundles with their replay commands.
5. **What the machine receives** (in `/etc/fenvix/runner.env`):
   - **`FENVIX_MODE`** = `shadow` (during the trial: run every test, report `wouldSkip`) or `enforce`.
   - **`FENVIX_REGION`** = `us` or `eu`.
   - **`FENVIX_MACHINE`** = `per-job` / `demo`. Until now that value was called `FENVIX_MODE`; **the runner must switch to the new names.**
