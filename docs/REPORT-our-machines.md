## 2. Final design (what the code does)

1. **Dispatcher** (`github-app/src/machines/pool.ts`, `launcher.ts`; `service.ts launchRunner`). A `workflow_job` queued webhook: the customer is the organization the App installation is linked to; the size is `runs-on: fenvix` (default size) or a second label `fenvix-<size>`; the region is the organization's. The pool, under a per-region advisory lock, picks in order: a free slot on a machine of THIS customer; the clean always-on machine; a stopped reserve machine (started with a new boot secret); a new machine (spot above `spotAbove` running machines). The just-in-time runner is registered at repository level for that one job (GitHub gives it no other job), with the job's labels. A job that gets no slot (customer caps, region full) waits in the database and takes the next free slot at once (job completion) or within a minute (the sweep). On `completed` the slot is freed, waiting jobs are dispatched, and the usage event records the machine's size, type, market and id.
2. **Machine-to-customer affinity**, enforced by the database (migration 0018): a machine's customer is set once and never changes; a used machine never becomes clean again (`gh_machines_one_customer` trigger, `gh_machines_clean` check); a lease's customer must be its machine's (`gh_leases_same_customer`). An empty machine lingers `lingerMinutes` for its customer, then is TERMINATED; the next customer gets a machine made from the clean image (a never-used reserve or a new one). So different customers never share a kernel, a disk, memory or a credential.
3. **Slots** (same customer): `infra/github-app/lib/runner/files/fenvix-slot`: per job its own user (fenvix-sN), a fresh home (0700), the GitHub runner copied from a root-owned template, its own mount namespace (the other slots are not mounted; `/tmp`, `/var/tmp`, `/dev/shm` private), its own PID namespace, no new privileges and no capabilities, cgroup limits (systemd scope); afterwards every process, file and System V object of the slot is removed.
4. **Always-on plus reserve.** `FENVIX_POOL` (cdk.json `pool`): one clean c7a.xlarge running (`alwaysOn: 1`), two prepared machines stopped (`reserve: 2`, only their EBS is paid), `maxMachines: 8` in the region, spot above 4 running, 3 machines and 6 concurrent jobs per customer by default (`workspaces.max_machines`, `max_concurrent_jobs` override). When the clean machine is taken, a reserve machine is started at once (ahead of need) and a new reserve is prepared. **Deviation from the approved wording:** the reserve is a dispatcher-managed pool of stopped instances, not an EC2 Auto Scaling warm pool. Same cost model (stopped, disk only), but an Auto Scaling group chooses which instance to scale in and could not keep the one-customer-per-machine rule or replace a used machine by terminating it.
5. **Credentials.** User data holds only plain settings and a single-use boot secret. The agent (`fenvix-agent`, root) exchanges it for a session credential (`/v1/runner/machine/hello`) and fetches each slot's work (`/v1/runner/machine/poll`): the just-in-time configuration and the JOB's own credentials, sealed in the database (AES-256-GCM bound to the lease id) and deleted when taken. The metadata service is refused to every uid but root.
6. **Trunk engine.** The image (`lib/runner/files/install.sh`, EC2 Image Builder) installs the fenvix-engine-cli trunk artifact by `engineVersion`, `engineUrl`, `engineSha256` (cdk.json), and the GitHub runner v2.338.2 by sha256 (`baebf204…147c40`, MEASURED: downloaded from github.com and hashed in this session). No pin, another checksum, a bad archive: the build stops. The version is in `/opt/fenvix/ENGINE`, reported at hello, and printed in every job log (`fenvix: engine <version> sha256=<sha256>`). Image tests run before distribution; the pipeline rebuilds weekly; the deploy waits for the build.
7. **Metering.** `ci_usage_events.machine_size`, `instance_type`, `machine_market`, `machine_id` per job; `gh_machine_minutes` per customer, region, size, market and day. No billing.
8. **Replays** (`kind: "replay"`): on a machine of the same customer, the run's commit is checked out with a one-hour read-only token, the engine rebuilds the defect under its stored seed and replays it N times (`fenvix repro TEST --seed S --confirm N --json`, engine trunk 71f8081); the machine reports `/v1/runner/replays`; verdict reproduced / flaky / passed against the stored fingerprint (`gh_replays`). **Exploration hook** (F-04): lease kind `exploration`, always a spot machine, never the always-on or a reserve machine.
9. **Results path.** The machine sends the job's summary (`FENVIX_OUT/summary.json`, read as the slot user) with the job's credential; progress and results keep the existing contract (`docs/data-contract.md`, now with the machine section, the engine contract of `FENVIX_MODE`/`FENVIX_SKIP`/`FENVIX_TEST_COMMAND`, and the optional `finished`/`workers` progress fields). Stop: Work `stop_run` (`now` cancels the GitHub run, `first_failure` fires on the first failed test), state on `gh_jobs.stop_state`.
10. **Shadow and skip-off safety.** Until the engine declares it honours `FENVIX_MODE` and `FENVIX_SKIP` (pool setting `engineHonoursMode`), such a job gets no shared-cache credential and an empty slot: nothing can be reused, every test runs.
11. **Retired:** per-job mode, demo mode (code, scripts, Lambda, tests) and the Firecracker spike.
